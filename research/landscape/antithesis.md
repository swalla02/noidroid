## What it is

A commercial autonomous testing platform built by people from the FoundationDB team. You
give it a container-composed deployment of your system; it runs the whole thing inside a
**deterministic hypervisor** — a fork of FreeBSD's bhyve they call "the Determinator" —
injects faults, and searches the state space for property violations. When it finds one,
the bug is perfectly reproducible and they can time-travel around it.

## How it works

The unit of reproducibility is **the whole VM**, not a process: "The Antithesis
environment simulates one or more computers using a collection of containers, all
running within a single virtual machine managed by our hypervisor."

- **Time.** All guest time sources (TSC, HPET) are virtualised; simulated time is "a
  function of only the deterministic state and execution history of the guest". Driven
  by the Intel PMC instructions-retired counter, which they had to work around because
  it miscounts about one instruction in 10^12.
- **Parallelism.** Not determinised — eliminated. One VM pinned per physical core.
  Guest-visible concurrency comes from the guest OS scheduler, which they control and
  reuse as a fault-injection surface (e.g. thread starvation).
- **I/O.** A custom `VMCALL`-based channel is the only opening in the box: the guest
  emits logs through it and ingests commands and RNG seeds through it.
- **Exploration.** "The points in execution history where the guest ingests input from
  the Antithesis platform become possible branch points … the external view of the
  exploration of a system is an input tree." Later extended so inputs also have an
  **injection time**, delivered by interrupt, rather than only being consumed when the
  guest asks. Branch selection is driven by an unpublished guidance component; the docs
  say it uses RL.
- They explicitly do **not** re-execute every path from the beginning: "We are not
  replaying every single execution path from the beginning – we would not waste your
  time like that!" Snapshots exist underneath as an optimisation.

## What it does that we should learn from

The input tree. Having bought total control of the machine, they still represent the
search as a tree of inputs consumed at boundary points, with machine snapshots as an
implementation detail underneath. That is our `Step`/`Action` model and our C2, chosen
by someone who had the alternative available. It is the strongest single piece of
evidence that "checkpoint = deterministic prefix, snapshot = fast path" is a design
position rather than a limitation. See `2026-08-21-input-tree-not-state-tree`.

Second: **injection time.** A pure input tree can only branch where the program chose to
ask; they found that insufficient and added preemptive delivery. We cannot copy this
without owning the runtime, and it names a real edge of our branching model.

Third, a disposition worth copying: the engineering post leads with the things that did
not work — the PMC miscounts, the APIC delivery jitter, the 50 GiB of trace per
20-minute run needed to find their own nondeterminisms.

## Where it is weaker, and why that is interesting

- **Throughput over latency, explicitly.** One VM per core, breadth-first. A developer
  running one counterfactual gets nothing from that architecture.
- **The interesting half is unpublished.** The post says outright it omits "all the
  functionality that allows efficient state exploration and time-travel debugging" for
  competitive reasons. Anyone reasoning about how they *choose* branches is guessing.
- **It is a service, not a thing you install.** The determinism lives in their
  datacentre on their hypervisor on their choice of Intel server CPUs.
- **It tests; it does not explain a run that already happened.** Their input tree is
  generated by search. Ours is generated by an execution someone actually performed.

## Overlap with us

Almost none as a product — different user (a team hardening a distributed system,
pre-release), different unit (a whole deployment), different aim (find unknown bugs
rather than explain a known run). The overlap is the *representation*: both systems
model counterfactual exploration as a tree over boundary inputs, and both refuse to make
a branch mean anything more than "the same prefix with one input different".

**Evidence standard:** verified by construction — determinism is enforced by the
hypervisor, so a reproduction is not a claim, it is a re-run. Stronger than ours in that
they need no oracle. Weaker in that it only holds inside their box; anything outside is
not tested at all.

## Watch triggers

- **The promised follow-up post on state exploration and time-travel debugging.** This is
  the most likely public source anywhere for how to choose branch points, which is our
  roadmap item 4 (guided multi-branch exploration) and which we have no theory of.
- Anything published about how they snapshot and restore VM state cheaply — bears on the
  snapshot fast-path.
- Their SDK surface growing: `assert_sometimes`-style properties and an SDK-provided
  randomness API would say that even with a deterministic hypervisor they still need the
  program to declare things, which is C1's argument from an unexpected direction.
